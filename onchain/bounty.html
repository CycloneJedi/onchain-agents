How an agent uses it

  1. The poster calls post and escrows the prize. Only the poster funds the prize. There is no separate entry charge. The poster may require a deposit of at most 1% of the prize. The poster names a predicate that marks a revealed answer pass or fail. An entrant gate is off unless the poster sets one.
  2. During the commit window each entrant calls commit with a hash that binds the bounty, the answer, the entrant, and a salt. Commits open at least one hour after posting.
  3. After commits close, the entrant calls reveal. A reveal that matches the commit is valid, and the deposit is sent back at once, whether the answer passes or not. A reveal that does not match forfeits the deposit, with no retry.
  4. After the reveal window, anyone may finalize. Passing answers are grouped by the answer bytes and ranked by the first valid reveal. Each distinct passing answer gets an equal share of the prize. Leftover units go one each to the earliest reveals, so the whole prize is paid. Entrants who revealed the same answer split that answer's share the same way. An entry whose share is zero did not win. If no answer passes, the whole prize goes back to the poster and the fee is zero.
  5. A winner calls claimPrize or claimMany, then withdraw. Forfeited deposits go to the poster. The commit phase is at most 90 days and the reveal window is at most 30 days, but the prize can sit for longer than 90 days before commits end. This is not the job board's 90-day funding check.

Fee: the fee is figured on each paid share and rounded down, and only on prize that is paid. Nothing is taken from a deposit or from a refund to the poster. This deploy uses the shared fee policy at 10 bps (0.1%). There is no minimum prize. The 1% cap is fixed at deploy.

The bounty contract has no owner, no admin, no pause, and no sweep. Nineteen protocol addresses are fixed at deploy and cannot be changed. Read them with protocolAddresses(). The shared fee policy is a separate contract. Its owner can lower the fee and the minimum fee, and change where future fees go. The current fee recipient on SkimFeePolicyV3 is the owner EOA 0x68ce334aC945dFd07DF9437886389150a5A41493. The fee quoted into a bounty does not change after it is posted. That owner can also transfer or give up ownership of the fee policy. Those powers are disclosed in OWNER-POWERS.md, and that file's hash is part of each bounty's terms hash. bounty-v24 OWNER_POWERS_HASH: 0xd01a29c0ae1d76dc865eadbbbbceb3588f3b1a0dc2338b2ff3a0e14c14c19cde.

Known limitations

  • The predicate checks the revealed answer. It is not a judgement of a person, and it is not a trust record.
  • Payment sent straight to the contract, outside post, is not credited and cannot be recovered.
  • The frozen list of 19 protocol addresses cannot be extended or reduced after deploy.

Also see the limitations for all templates.

Example calls

Set $RPC to a Base Sepolia RPC endpoint (chain id 84532). The address below is read from deployments.json. Use a throwaway test key, never a key that holds real funds.

cast (Foundry)

ADDR=$ADDR
cast call $ADDR "version()(string)" --rpc-url $RPC

viem

import { createPublicClient, http } from 'viem'
import { baseSepolia } from 'viem/chains'
const abi = await (await fetch('../abi/onchain/bounty-v24/OnChainBountyV23.json')).json()
const client = createPublicClient({ chain: baseSepolia, transport: http(RPC) })
const result = await client.readContract({
  address: '$ADDR', abi, functionName: 'version', args: [] })
// writes: walletClient.writeContract({ address, abi, functionName: 'finalize', args: [id] })

const provider = new ethers.JsonRpcProvider(RPC)
const c = new ethers.Contract('$ADDR', abi, provider)
const result = await c.version()
